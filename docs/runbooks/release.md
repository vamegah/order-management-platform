# Signed release and approved promotion

Status: implementation under verification. Local drills do not constitute a production deployment. A protected staging/production destination, named approvers and its dedicated runner must be provisioned before enabling promotion.

The supported topology is a dedicated Linux amd64 Docker Compose host. Use the standalone `docker-compose.prod.yml` with a cryptographically verified image overlay. Development Compose files and their credentials are excluded. Inventory/payment each have one replica and are stopped before replacement. PostgreSQL, Kafka and Redis remain on private networks; payment and webhook delivery have outbound connectivity without published host ports. This is a single-host availability model, not a multi-zone deployment.

## Prepare the host

1. Install Docker Engine/Compose, Python 3, the systemd units in this repository, and a dedicated GitHub runner labelled `omp-release`. Restrict runner use to this protected repository. Create runtime group 2000. Reserve UID 65534 for monitoring processes on this dedicated host.
2. Check out the accepted source under `/opt/omp`. Create `/etc/omp/config`, a private secret directory, separate TLS identity/trust directories and an independently mounted backup repository. Provision the backup directory for PostgreSQL UID 70, group 2000, mode 0770. Back up the repository encryption key through an independently controlled secret manager; the generator never prints it.
3. Prepare one bcrypt ingress administrator entry with cost 12?16 using an interactive password tool. Run `sudo python3 scripts/prepare_production_secrets.py --directory /etc/omp/secrets --htpasswd-file /secure/operator.htpasswd`. It refuses overwrites and symlink destinations. Internal credentials are random files, mode 0440, root:2000; external Stripe credentials are supplied separately as `stripe_api_key` and `stripe_webhook_secret`. Never put values in `.env` or shell arguments.
4. Provision the banking PKCS12 identity and trust stores using [the SOAP procedure](../soap-operations.md). Generated `bank-ledger`/`bank-adapter` config trees share the verified database and WS-Security credentials. Use their generated key-store/trust-store password files when preparing the stores. Mount issuer public trust only into workloads; keep CA signing keys outside them. Publish the five public leaf certificates separately for the certificate exporter.
5. Provision the `omp` realm in the production issuer. No development realm/users are imported. Configure public tokens with audience `omp-api`; recovery tokens retain their explicit service audiences and `order.reconcile` scope. Create a confidential metrics client with only `metrics.read` and audience `omp-api`; do not grant administrator roles. Store its credential as `/etc/omp/secrets/metrics_client_secret`.
6. Configure `/etc/omp/metrics-token.env` with HTTPS `SERVICE_TOKEN_URL`, `SERVICE_TOKEN_ISSUER`, `SERVICE_TOKEN_CLIENT_ID`, `SERVICE_TOKEN_SCOPE=metrics.read`, and `SERVICE_TOKEN_AUDIENCES=omp-api`. Install/start `infrastructure/identity/omp-metrics-token.service`. Systemd loads the private credential; the projection runs as UID 65534, refreshes atomically and is mounted as a directory into Prometheus. The production projector never follows redirects or enables development HTTP.
7. Render ingress with `python3 scripts/render_ingress.py --domain example.com --output /etc/omp/config/ingress-routes.json`. Put the HTTPS recording/operations receiver URL in a private file without embedded credentials or query strings. Render Alertmanager with `python3 scripts/render_alertmanager.py --url-file /secure/receiver-url --output /etc/omp/config/alertmanager.json`; provision its bearer credential file separately. Configuration rendering never emits credential values.
8. Copy `.env.prod.example` to `/etc/omp/staging.env` or `/etc/omp/production.env`; set only domain, contact and managed paths. DNS must cover `api`, `auth`, `keycloak-admin`, `grafana`, `prometheus` and `traefik` below the selected domain. Only ports 80/443 are public. The API endpoint is `https://api.<OMP_DOMAIN>`.

## Publish a release

Configure strict, administrator-enforced main protection with required `quality-gate`. Configure an active release-tag ruleset covering the selected `refs/tags/v*` identity, forbidding updates/deletion without bypass. A read-only GitHub App policy credential (`RELEASE_POLICY_READ_TOKEN`) needs repository Administration, Actions and Contents read permissions. It is separate from package publication credentials.

After the exact main commit passes all required verification, create a semantic release tag. `release.yml` verifies branch protection, tag protection and the exact successful main workflow. It builds nine applications and the backup-capable PostgreSQL image, scans all owned and locked infrastructure images, creates SBOMs/build provenance, and signs image digests, attestations and the release manifest with the GitHub workflow identity. High/critical vulnerabilities fail publication, including unfixed findings. The release includes a reviewed migration manifest; changing accepted SQL or adding unreviewed migrations fails. Source timestamps make application archives reproducible for a fixed accepted build input.

`release_policy.py` verifies the GitHub issuer, workflow/tag identity and workflow SHA, exact image subject, SBOM/provenance predicate and every evidence hash. It rejects missing/unsigned/tampered inputs, foreign repositories, debug services and mutable image references. Upstream infrastructure is trusted by reviewed digest and its scan is bound into the signed release bundle.

## Promote or roll back

Configure GitHub environments `staging` and `production` with named required reviewers, prevention of self review, no administrator bypass and restricted deployment branches. Host access is through the dedicated runner and managed files; it is not embedded in the release. Dispatch `promote.yml` from protected main with the existing release, destination and `promote` or `rollback` action. The policy job checks environment protection before the deployment job requests approval.

The job verifies signed inputs before checking out their exact source. The driver then verifies them again, checks the resolved production policy, re-scans against the current vulnerability database, takes an exclusive deployment lock and checks the backup archive before modifying an existing deployment. It stops the process-local stream owners, pulls exact digests and waits for health. A failed deployment preserves signed pending and previous release evidence. It never deletes database volumes or credentials.

For rollback, dispatch the same approved workflow with the earlier signed release and `rollback`. Database migrations are never reversed. The earlier schema must be unchanged or explicitly compatible in the signed review. Changes to stateful infrastructure/runtime inputs require a separate storage upgrade procedure; application rollback does not authorize a storage-format downgrade. A rebuild with unchanged PostgreSQL runtime inputs is allowed. All chosen images must still pass the current vulnerability policy.

Before applying changes, the operator can run `promote_release.py` with the same file arguments and omit `--execute` to print a verified plan. Production promotion acceptance additionally requires recording the destination, approver, release digests, health/conservation checks and rollback result. No production destination has been supplied for this local implementation run.

The private `ops` network contains monitoring and ingress administration. Traefik has no database-network attachment; Alertmanager has a separate egress attachment for authenticated receiver delivery. Keep accepted source checkouts and overlays under the persistent promotion state directory: active bind mounts and the backup timer depend on those files.
